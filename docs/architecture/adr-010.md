# ADR 010: CLOB-Aware Mempool with Gas Ratio Reservation

## Changelog
* 2026-03-02: first draft

## Context

Cronos has a CLOB (Central Limit Order Book) exchange module (`x/exchange`) where an off-chain sequencer submits batches of matched trades on-chain via `MsgSettleBatch`. These settlement transactions are latency-sensitive — delays directly impact the trading experience for users.

In the current architecture, CLOB settlement transactions compete with regular EVM transactions in a single `PriorityNonceMempool`. During periods of high EVM activity, settlement batches can be delayed or crowded out entirely, degrading CLOB performance. There is no mechanism to guarantee block space for settlement transactions or to place them at predictable positions within a block.

### Goals

1. **Prioritize** CLOB transactions so they always appear at the front of every block.
2. **Reserve** a configurable fraction of block gas for CLOB transactions so they cannot be crowded out by regular EVM traffic.
3. **Roll over** unused CLOB gas quota to regular EVM transactions so no block space is wasted.
4. **Zero impact** on existing behavior when the feature is disabled (`clob-gas-ratio = 0`).

## Decision

### Two-Pool Mempool Architecture

Replace the single `PriorityNonceMempool` with a `CLOBMempool` that contains two independent sub-pools:

```
CLOBMempool
├── clobPool    (PriorityNonceMempool) ← MsgSettleBatch txs
└── regularPool (PriorityNonceMempool) ← all other txs
```

Transaction routing is determined at insertion time by inspecting `tx.GetMsgs()` for `*exchangetypes.MsgSettleBatch`. The `SelectBy` method iterates `clobPool` first, then `regularPool`, ensuring CLOB transactions always appear before regular transactions in block proposals.

Both sub-pools share the same `SignerExtractionAdapter` and `TxReplacement` policy, preserving existing nonce-priority and fee-bump semantics within each pool.

### Gas Ratio Reservation in Block Proposals

A new `CLOBTxSelector` (implementing `baseapp.TxSelector`) enforces gas budgets during `PrepareProposal`:

```
Block Gas Budget (maxBlockGas)
├── CLOB Phase:    up to  clobGasRatio × maxBlockGas
└── Regular Phase: up to  maxBlockGas − clobGasUsed  (rollover)
```

Key semantics:
- **CLOB phase**: When a CLOB tx exceeds the remaining CLOB gas quota, it is **skipped** (continue iterating). This allows smaller CLOB txs to still fit.
- **Regular phase**: When a regular tx exceeds the effective limit (including rollover), the selector **halts** (no more txs will fit).
- **Rollover**: `effectiveRegularLimit = maxBlockGas − clobGasUsed`. If no CLOB txs are in the mempool, regular txs get the full block gas budget.
- **Unlimited gas**: When `maxBlockGas = 0`, gas checks are bypassed entirely; only the byte budget applies.
- **Lazy initialization**: The gas limits are computed on the first `SelectTxForProposal` call and reset via `Clear()` at the end of each block.

### Conditional Activation

The feature is controlled by a single config parameter:

```toml
[cronos]
clob-gas-ratio = 0.0  # disabled by default
```

Three mempool configurations are supported:
1. `clobGasRatio > 0` with valid mempool settings → `CLOBMempool` + `CLOBTxSelector`
2. `clobGasRatio = 0` (or unset) with valid mempool settings → `PriorityNonceMempool` + `ExtTxSelector` (unchanged)
3. Mempool disabled → `NoOpMempool` (unchanged)

The selector condition checks `mpool.(*CLOBMempool)` directly rather than re-checking `clobGasRatio`, ensuring the selector and mempool types are always consistent.

### Safety Measures

- **Ratio clamping**: `clobGasRatio` is clamped to `[0.0, 1.0]` at startup. Values > 1.0 would cause uint64 underflow in the rollover calculation (`maxBlockGas − clobGasUsed`); the clamp prevents this.
- **Nil-tx guard**: If the tx decoder returns `(nil, nil)`, the selector skips the tx instead of panicking on `nil.GetMsgs()`.
- **Type-safe activation**: The `CLOBTxSelector` is only installed when the mempool is actually a `*CLOBMempool`, preventing a mismatch if `clobGasRatio > 0` but the mempool is `NoOpMempool` (e.g., due to `mempool-max-txs = -1`).

## Status

Proposed

## Consequences

### Positive

- CLOB settlement transactions get guaranteed block placement (always first) and reserved gas capacity.
- Unused CLOB gas quota rolls over to regular transactions — no block space is wasted.
- Zero behavioral change when `clob-gas-ratio = 0` (default). Existing nodes are unaffected.
- Each sub-pool retains full `PriorityNonceMempool` functionality (priority ordering, nonce tracking, fee-bump replacement).

### Negative

- Two `PriorityNonceMempool` instances per node doubles memory usage for mempool indexing structures. In practice the overhead is small compared to the stored transactions themselves.
- The `MaxTx` configuration applies per-pool, so the effective maximum is `2 × MaxTx`. This is intentional (each pool has independent capacity) but may surprise operators expecting a combined limit.
- `CLOBMempool.Remove` tries `clobPool` first for all txs; regular tx removals incur one extra failed lookup. This is a minor inefficiency for robustness.

### Neutral

- The CLOB detection logic (`isCLOBTx`) inspects `tx.GetMsgs()` for `*exchangetypes.MsgSettleBatch`. If additional CLOB message types are introduced in the future, this function must be updated.
- The `CLOBTxSelector` reuses the same `ValidateTransaction` blocklist logic as `ExtTxSelector`, so blocklist enforcement is preserved.
