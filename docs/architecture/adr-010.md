# ADR 010: CLOB-Aware Mempool with Block Ratio Reservation

## Changelog
* 2026-03-02: first draft
* 2026-03-03: extend ratio to cover both gas and bytes; rename `clob-gas-ratio` → `clob-block-ratio`
* 2026-03-03: switch CLOB detection from message-type (`MsgSettleBatch`) to sender-address (`clob-sequencer-address`)

## Context

Cronos has a CLOB (Central Limit Order Book) exchange module (`x/exchange`) where an off-chain sequencer submits settlement transactions on-chain as standard `MsgEthereumTx` messages. These transactions are latency-sensitive — delays directly impact the trading experience for users.

In the current architecture, CLOB settlement transactions compete with regular EVM transactions in a single `PriorityNonceMempool`. During periods of high EVM activity, settlement batches can be delayed or crowded out entirely, degrading CLOB performance. There is no mechanism to guarantee block space for settlement transactions or to place them at predictable positions within a block.

### Goals

1. **Prioritize** CLOB transactions so they always appear at the front of every block.
2. **Reserve** a configurable fraction of block resources (gas **and** bytes) for CLOB transactions so they cannot be crowded out by regular EVM traffic.
3. **Roll over** unused CLOB quota to regular EVM transactions so no block space is wasted.
4. **Zero impact** on existing behavior when the feature is disabled (`clob-block-ratio = 0`).

## Decision

### Two-Pool Mempool Architecture

Replace the single `PriorityNonceMempool` with a `CLOBMempool` that contains two independent sub-pools:

```
CLOBMempool
├── clobPool    (PriorityNonceMempool) ← sequencer txs (CLOB)
└── regularPool (PriorityNonceMempool) ← all other txs
```

Transaction routing is determined at insertion time by checking whether the
`MsgEthereumTx` sender matches the configured sequencer address
(`clob-sequencer-address`). The detection logic is created via
`NewCLOBTxDetector(sequencerAddr)` which returns a `func(sdk.Tx) bool` closure.
The `SelectBy` method iterates `clobPool` first, then `regularPool`, ensuring
CLOB transactions always appear before regular transactions in block proposals.

Both sub-pools share the same `SignerExtractionAdapter` and `TxReplacement` policy, preserving existing nonce-priority and fee-bump semantics within each pool.

### Block Ratio Reservation in Block Proposals

A new `CLOBTxSelector` (implementing `baseapp.TxSelector`) enforces both gas and byte budgets during `PrepareProposal`:

```
Block Gas Budget (maxBlockGas)
├── CLOB Phase:    up to  clobBlockRatio × maxBlockGas
└── Regular Phase: up to  maxBlockGas − clobGasUsed  (rollover)

Block Bytes Budget (maxTxBytes)
├── CLOB Phase:    up to  clobBlockRatio × maxTxBytes
└── Regular Phase: up to  maxTxBytes − clobBytesUsed  (rollover)
```

Key semantics:
- **CLOB phase**: When a CLOB tx exceeds the remaining CLOB gas **or** byte quota, it is **skipped** (continue iterating). This allows smaller CLOB txs to still fit.
- **Regular phase**: When a regular tx exceeds the effective byte or gas limit (including rollover), the selector **halts** (no more txs will fit).
- **Gas rollover**: `effectiveRegularGasLimit = maxBlockGas − clobGasUsed`. If no CLOB txs are in the mempool, regular txs get the full block gas budget.
- **Byte rollover**: `effectiveRegularBytesLimit = maxTxBytes − clobBytesUsed`. Same rollover semantics apply to the byte budget.
- **Unlimited gas**: When `maxBlockGas = 0`, gas checks are bypassed entirely; byte budgets still apply.
- **Lazy initialization**: Both gas and byte limits are computed on the first `SelectTxForProposal` call and reset via `Clear()` at the end of each block.

### Conditional Activation

The feature is controlled by two config parameters:

```toml
[cronos]
clob-block-ratio = 0.0       # disabled by default
clob-sequencer-address = ""   # bech32 address of the CLOB sequencer
```

The `CLOBMempool` is created only when `clobBlockRatio > 0` **and** `clob-sequencer-address` is non-empty.

Three mempool configurations are supported:
1. `clobBlockRatio > 0` with valid sequencer address and mempool settings → `CLOBMempool` + `CLOBTxSelector`
2. `clobBlockRatio = 0` (or unset) with valid mempool settings → `PriorityNonceMempool` + `ExtTxSelector` (unchanged)
3. Mempool disabled → `NoOpMempool` (unchanged)

The selector condition checks `mpool.(*CLOBMempool)` directly rather than re-checking `clobBlockRatio`, ensuring the selector and mempool types are always consistent.

### Safety Measures

- **Ratio clamping**: `clobBlockRatio` is clamped to `[0.0, 1.0]` at startup. Values > 1.0 would cause uint64 underflow in the rollover calculations; the clamp prevents this.
- **Nil-tx guard**: If the tx decoder returns `(nil, nil)`, the selector skips the tx instead of panicking on `nil.GetMsgs()`.
- **Type-safe activation**: The `CLOBTxSelector` is only installed when the mempool is actually a `*CLOBMempool`, preventing a mismatch if `clobBlockRatio > 0` but the mempool is `NoOpMempool` (e.g., due to `mempool-max-txs = -1`).

## Status

Proposed

## Consequences

### Positive

- CLOB settlement transactions get guaranteed block placement (always first) and reserved gas + byte capacity.
- Unused CLOB quota (both gas and bytes) rolls over to regular transactions — no block space is wasted.
- Zero behavioral change when `clob-block-ratio = 0` (default). Existing nodes are unaffected.
- Each sub-pool retains full `PriorityNonceMempool` functionality (priority ordering, nonce tracking, fee-bump replacement).

### Negative

- Two `PriorityNonceMempool` instances per node doubles memory usage for mempool indexing structures. In practice the overhead is small compared to the stored transactions themselves.
- The `MaxTx` configuration applies per-pool, so the effective maximum is `2 × MaxTx`. This is intentional (each pool has independent capacity) but may surprise operators expecting a combined limit.
- `CLOBMempool.Remove` tries `clobPool` first for all txs; regular tx removals incur one extra failed lookup. This is a minor inefficiency for robustness.

### Neutral

- The CLOB detection logic uses a sender-address check (`NewCLOBTxDetector`) against the configured `clob-sequencer-address`. If the sequencer address changes (e.g., via governance in the future), the node must be restarted with the new address.
- The `CLOBTxSelector` reuses the same `ValidateTransaction` blocklist logic as `ExtTxSelector`, so blocklist enforcement is preserved.
